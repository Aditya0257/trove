Trove architecture guide

Trove is a private vault for the documents that matter: bills, receipts, policies, warranties, IDs. You photograph or upload a document; Trove reads it, files it by category, extracts the key fields, and layers spend tracking, anomaly alerts, reminders, and natural-language search on top.

The audience is small and trusted, on the order of 50 to 100 users with roughly 10 active at once, and the whole system runs on free infrastructure tiers. That shapes every priority: optimise for reliability and zero data loss, not for scale to millions. This guide is the visual map of the system; the full written documentation lives in the repository under docs/ and is indexed at the end.

The core principle

The app is disposable. The data is not. Losing the entire app, database, and host must lose zero documents.

Three non-negotiable rules follow directly, and they are why storage, sidecars and backup are first-class parts of the system rather than afterthoughts.

  1. The uploaded image or PDF is the only source of truth. Files live in object storage. The database is a rebuildable index; if it is wiped, it is rebuilt by scanning the bucket.
  2. Every file has a sidecar JSON beside it holding its metadata, so the object store is self-describing and independently meaningful.
  3. Three independent copies exist, one human-browsable without the app: Cloudflare R2 (hot), Backblaze B2 (mirror), and Google Drive (a readable folder tree).

System context

Two thin clients over one stateless backend, three independent storage tiers, and a small set of external services. Documents can also arrive with no client at all, by forwarding email to a per-space address.

Modules

The backend is organised package-by-feature: each module owns its controller, service, repository and domain types, and modules talk through interfaces (StorageService, ExtractionProvider, EmbeddingProvider) and after-commit events, so providers are swappable and features stay decoupled.

document

Upload, list, confirm, soft delete, restore, purge, export, import. Owns the lifecycle and sidecar writes.

storage

The S3-compatible seam; sidecar read/write; presigned URLs. Same code for R2 and MinIO.

extraction

The provider fallback chain, the async worker, and the AI budget guard.

auth

Stateless JWT, TOTP two-factor, password reset, sign-up email verification (OTP), admin approval and account deletion, and self-service profile (name, email, photo).

space

Personal and shared spaces, roles, invitations, join links, ingest addresses.

reminder

Due, renewal and warranty reminders; recurrence; auto-creation; dispatch.

chat

Retrieval-augmented "Ask your vault": embeddings, grounded answers, routing.

search

Natural-language search, AI-first with a rule-based fallback.

anomaly

Flags a bill higher than usual for its category, at confirm time.

analytics

Spend aggregation by category and by month over confirmed documents.

drive

Google Drive OAuth, pooled multi-Drive sync, quota tracking.

backup

pg_dump, the B2 mirror, and the full export or import ZIP.

integrity

Verifies the three tiers agree; reports what is rebuildable.

ingestion

Forward-to-file email and WhatsApp webhooks.

mail

Filed emails grouped into threads by a shared bundle id; a paginated thread list and a single-thread view.

Deployment topology

A single stateless jar with no durable state on disk, so the host is disposable: if the instance is reclaimed, redeploy the jar and point it at the same Neon, R2, B2 and Drive, and the system is whole. Scheduled work runs in-process on fixed delays; at this scale that is correct and far simpler than a separate scheduler.

The request lifecycle

Every authenticated request follows the same path, so security and feedback are uniform. Authentication is a stateless JWT; authorization is a per-space membership-and-role check in the service; and any thrown error is turned into a Notice envelope by a single global handler, never a raw stack trace.

Data model

Twenty tables. The database holds metadata and extracted text only, never the files, and is a rebuildable projection of the sidecars in object storage. Flyway owns the schema across migrations V1 to V25; Hibernate only validates it.

Capture to confirm

The core path. Extraction is asynchronous and always lands in needs_review; a human confirms the fields before a document is trusted, because the AI will misread an amount or a date. Confirming is what makes a document count toward spend, become searchable, and generate reminders.

Several files can be uploaded at once, and each becomes its own separate document. Images are read by the vision model when the "Read images with AI" toggle is on; PDFs are stored safely but are not auto-read yet, so they go straight to manual review. This is unlike Mail, where several screenshots are grouped into a single email thread.

Resilience and backup

A document is safe the instant it is in R2 with its sidecar. Everything else is redundancy, on independent providers with independent failure modes. Tier 3 is deliberately human-navigable, so in the worst case a person opens Google Drive and finds the document with no software involved.

Tier 1
Cloudflare R2, hot

Live reads and writes, written synchronously on upload. Files plus self-describing sidecars.

Tier 2
Backblaze B2, mirror

Hourly, idempotent key-diff copy to a different provider. Append-only, so a purged document still has an archival copy.

Tier 3
Google Drive, human-browsable

Per-space-owner OAuth into a readable tree: Trove / space / category / month. Pools several Drives (rotate or mirror).

Deleting is a soft delete with a 30-day recovery window: the file moves to a _trash/ prefix and the Drive copy to _Deleted, reversible by restore, then purged by a daily job. An on-demand export ZIP (a complete manifest.json, a spreadsheet data.csv, and the original files/) restores the whole system, even onto a fresh deployment. A daily integrity check verifies all three tiers actually agree.

AI and retrieval

AI is used to read documents, to embed them for semantic search, to answer questions grounded in the vault, and to parse search queries. Every path is built around two constraints: the AI is never trusted blindly, and everything stays inside a shared free daily budget (10,000 neurons per day, with a per-user cap).

Ask your vault (RAG)

Questions are answered strictly from the user's own documents, with citations, and the assistant refuses rather than inventing when nothing relevant is found.

Extraction downscales images and reads images only; indexing uses a tiny embedding model; answering routes to the cheapest adequate model; search and anomaly fall back to rules and arithmetic. Every path degrades rather than failing. That is how a genuinely useful AI feature set fits inside a free tier.

Because the documents are English (Indian bills and receipts) and the embedding model is English-only, a Hindi or Hinglish question ("kya meri saari tax receipts dikhao") would otherwise match nothing. So the question is first normalized to an English search query before it is embedded: a cheap heuristic passes plain English through untouched, and only a likely non-English question spends one tiny classifier call, falling back to the original text on any error. Retrieval, reminder detection and the grounded answer all run on the normalized query, so the English corpus keeps its English embedder with no multilingual model or re-index.

Security and access

Authentication is a stateless JWT (12-hour default), optionally reinforced by a TOTP second factor. Sign-up is gated in two steps: a new account starts unverified and must confirm a 6-digit code emailed to it, then it becomes pending until a configured admin approves it (active). Admins are an allow-list of one or more emails, set purely by configuration with no privileged flag in the database. Authorization is per space: a document belongs to exactly one space, and rights are decided by the caller's role there.

Vital documents (passport, ID, policies) are encrypted at rest with AES-256-GCM through a single storage seam, and served through a decrypt-stream path rather than a public link. The same service encrypts stored TOTP secrets and Google refresh tokens. Secrets come from environment variables only.

Users manage their own account from a profile screen: display name, profile photo, an email change confirmed by an OTP to the new address, and a password change that re-checks the current one. Deleting an account is deliberately admin-only and irreversible: it purges every document in the user's spaces from R2, Google Drive and the database, guarded so an admin cannot delete themselves or another admin and must re-type the target's exact email. The append-only B2 mirror still keeps an archival copy.

Reminders lifecycle

Reminders are due, renewal or warranty nudges, created by hand or automatically from a confirmed document (type-aware, plus warranty dates and detected subscription cadences). A recurring reminder schedules its next occurrence when marked done, so the series advances exactly once.
